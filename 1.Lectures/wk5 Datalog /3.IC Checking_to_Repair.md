# Lecture: Integrity Constraint (IC) Checking and Repair

## ✅ Summary

This lecture extends the use of **Datalog** from **integrity constraint checking** to **database repair** when violations occur. The focus is on detecting and resolving **functional dependencies (FDs)** and **inclusion dependencies (IDs)**, including **foreign key violations**.

Key points:
- **Dirty data** = data that violates logical constraints (e.g., duplicate keys, missing foreign key references)
- IC violations can be detected via **queries** in Datalog or SQL
- **Minimal repair**: modify the smallest possible part of the database to restore consistency
- **ASP/DLV** systems extend Datalog to support **disjunctive rules** and **possible world semantics**, generating all possible repairs
- Repairs are not unique; multiple valid "worlds" exist
- Goal: automate repair generation while understanding trade-offs and computational limits

---

## 📚 Details

### 🔸 Types of Integrity Constraints

| Constraint Type       | Description                                 | Example                        |
|-----------------------|---------------------------------------------|--------------------------------|
| **Functional Dependency (FD)** | Key constraint: 1 key → 1 value         | Student ID should map to 1 name |
| **Inclusion Dependency (ID)** | Foreign key constraint: FK → PK        | Enrollment.StudentID must exist in Student table |

---

### 🔸 Detecting Violations

- Example: Student table with:
  - **101 → John Bell**
  - **101 → Joe Logan**  
  → FD violation (ID 101 mapped to multiple names)

- Example: Enrollment table:
  - Contains StudentID 105, but no such student in Student table
  → Foreign key violation

Detection = writing **Datalog or SQL queries** to find "bad guys."

---

### 🔸 Minimal Repairs

- Goal: Fix violations with **minimal changes** to preserve as much data as possible
- Avoid trivial "repair" (e.g., deleting all data)
- Example:
  - FD violation (101 → Bell, Logan) →  
    Repair = delete either Bell or Logan’s entry

---

### 🔸 Disjunctive Repairs with ASP/DLV

- Regular Datalog and SQL: can't express **choices** (either this or that)
- **ASP/DLV** enables:
  - Rules with **disjunction** (logical OR)
  - Generates multiple **possible worlds** (repairs)
- Each repair is a consistent version of the data:
  - Repair 1: 101 → Bell
  - Repair 2: 101 → Logan

---

### 🔸 Repair Semantics: Possible Worlds

- Each repair is a **possible world**:
  - A minimal, consistent version of the data
- Systems like ASP/DLV explore these possibilities automatically
- Trade-off: Expressiveness vs. Efficiency:
  - Power of disjunctive logic = more computationally intensive

---

### 🔸 Practical Implications

- ASP/DLV is a **constraint solver**, not just a query engine
- Automates finding **all minimal repairs**
- Useful for complex cases, but may not scale to massive datasets

---

> 🧠 Takeaway: IC checking finds problems; repair proposes **multiple valid solutions**—your job is to **choose wisely**.
