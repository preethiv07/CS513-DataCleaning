# Lecture: Demonstrating Complementary Provenance

## ✅ Summary

This lecture showcases a collaboration between two complementary tools: **YesWorkflow** and **noWorkflow**, which address different ends of the provenance spectrum. The goal is to demonstrate how **prospective provenance** (YW) and **retrospective provenance** (nW) can be integrated to give a richer understanding of data processing workflows—especially when using **Python scripts**. 

Key points:
- **YesWorkflow (YW)** models conceptual, planned workflows from annotated scripts.
- **noWorkflow (nW)** captures fine-grained runtime execution traces of Python scripts.
- Together, they enable both high-level understanding and detailed execution tracking.
- This combined approach is useful when no formal workflow system is used.
- Provenance can be used to answer questions about data lineage and processing dependencies.

---

## 📚 Details

### 🔸 Overview of YesWorkflow vs. noWorkflow

| Tool          | Focus                      | Provenance Type         | Characteristics                                |
|---------------|----------------------------|--------------------------|------------------------------------------------|
| YesWorkflow   | Conceptual structure       | **Prospective**          | Script annotations (@BEGIN, @IN, @OUT), language-agnostic |
| noWorkflow    | Execution behavior         | **Retrospective**        | Python-only; captures function calls, variable values, runtime traces |

---

### 🔸 Complementary Strengths

- **YW**: Ideal for declaring intended workflow structure, even in the absence of execution.
- **nW**: Ideal for analyzing what actually happened during script execution.
- Combined use enables:
  - High-level understanding (**YW**)
  - Fine-grained, code-level debugging (**nW**)

---

### 🔸 Use Case Demonstration

- A Python script was annotated with **YesWorkflow** to show the conceptual data flow.
- The same script was executed using **noWorkflow**, which captured:
  - Function calls
  - Variable states
  - File accesses

These two sets of provenance were visually combined to answer complex questions about the script’s behavior.

---

### 🔸 Example Questions Answered

- What is the lineage of `corrected_image`?
- What upstream inputs influenced a specific result?
- What was the function call path that produced a certain output?
- How does runtime behavior compare to the planned model?

---

### 🔸 Technical Insights

- **YesWorkflow** builds diagrams from annotations; no script execution is needed.
- **noWorkflow** instruments Python code using a profiling library.
- Both systems support **visual graphs** of provenance.
- **Fine-grained provenance** from nW can be overwhelming but is valuable for tracing bugs or understanding performance.

---

### 🔸 Challenges and Solutions

- **Scripts ≠ Workflows**: Scripts lack built-in provenance or structural clarity.
- **Bridging the Gap**:
  - Use YW for planned abstraction.
  - Use nW for detailed runtime behavior.
  - Merge both for full provenance.
- **Workflow Systems** (e.g., Kepler) provide both prospective and retrospective views by design. For scripts, this must be reconstructed manually.

---

### 🔸 Standards Context

- **W3C PROV** and **OPM** models focus primarily on **retrospective provenance**.
- **ProvONE** extends W3C PROV to include **workflow structure** for **DataONE**.
- This supports hybrid provenance graphs combining both planning and execution.

---

> 🧠 The takeaway: You don’t need to choose between conceptual clarity and execution detail. With YesWorkflow and noWorkflow, you can have both—and gain powerful insight into your data science process.
