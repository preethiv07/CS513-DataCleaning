# Lecture: Provenance Standards

## ✅ Summary

This lecture introduces the concept of **provenance standards**, focusing on the **W3C PROV model**, its limitations, and the need for extensions like **ProvONE**. It emphasizes the distinction between **prospective provenance** (workflow design) and **retrospective provenance** (what actually happened) in scientific workflows.

Key takeaways:
- **Prospective provenance** = the workflow recipe (Workflow-land)
- **Retrospective provenance** = execution traces (Trace-land)
- **W3C PROV** is the main standard for retrospective provenance but lacks workflow-level modeling.
- **ProvONE** extends PROV to integrate workflow structure and execution history.
- Capturing provenance is challenging, and tools must offer **value for the creator** (Provenance for Self), not just for others.

---

## 📚 Details

### 🔸 Key Concepts

| Term                      | Definition                                               |
|---------------------------|----------------------------------------------------------|
| **Prospective Provenance** | The workflow plan: a recipe of data analysis steps      |
| **Retrospective Provenance** | The actual execution history: logs, traces, outputs    |
| **Workflow-land**         | The schematic, abstract design of a workflow (plan)     |
| **Trace-land**            | The detailed execution results (what really happened)    |

---

### 🔸 W3C PROV Standard

- Focuses on **retrospective provenance**:
  - Defines concepts like:
    - **Used** (data read)
    - **GeneratedBy** (data produced)
- Does **not** include workflow modeling:
  - No representation of **workflow structure** or dataflow.
  - This limits how well provenance can support debugging or reproducibility in scientific workflows.

---

### 🔸 ProvONE Extension

- Developed to bridge **workflow design** and **execution**:
  - Integrates workflow structures (prospective) with traces (retrospective).
  - Helps answer questions like:
    - Did the execution follow the designed workflow?
    - Which data products came from which processing steps?

---

### 🔸 Benefits and Challenges

| Aspect                    | Challenge                                           | Need                                           |
|---------------------------|----------------------------------------------------|-----------------------------------------------|
| Capturing Provenance      | Tedious; scientists deprioritize it                | Tools that provide immediate value (Provenance for Self) |
| Using Provenance          | Limited unless tools exist for analysis            | Provenance queries to aid debugging, validation |
| Community Practice        | Provenance seen as metadata for others             | Shift to **Provenance for Self** mindset       |

---

### 🔸 Real-World Applications

- **Provenance for Self**:
  - Helps **debug studies early** (catch mistakes before publication)
  - Supports **transparency and reproducibility** post-publication

- Example: **National Climate Assessment (GCIS)**:
  - Tries to trace findings (graphs, conclusions) back to data and code.
  - Painstaking process; often retrofitted from scattered sources.

---

### 🔸 Final Thought

> 🧠 Provenance must move from "metadata for others" to "metadata for yourself" — an active, helpful tool for scientists.
